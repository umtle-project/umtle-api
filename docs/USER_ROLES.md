# 움틀 사용자 역할 및 권한

이 문서는 움틀(Umtle)의 사용자 역할과 도메인별 권한을 관리한다. 문서 우선순위는 `AGENTS.md`를 따르며, 이 문서는 `PRD.md`, `REQUIREMENTS.md`의 범위를 벗어나지 않는다.

이 문서는 `REQUIREMENTS.md` 3장에 이미 서술된 역할별 권한 문장을 도메인 × 역할 표로 정형화한 것이다. 여기에 서술되지 않은 권한은 원본 문서에도 서술이 없는 것이며, 이 문서에서 임의로 새로 정하지 않는다 — 해당 항목은 4장 "아직 결정되지 않은 사항"에 명시한다.

---

## 1. 목적

- `REQUIREMENTS.md` 3장의 역할별 권한 서술을 도메인 × 역할 매트릭스 형태로 정리해, 참조하기 쉬운 단일 기준을 제공한다.
- `DOMAIN_MODEL.md` 3.1 사용자(User) 도메인에서 참조하는 "역할별 상세 권한과 접근 범위"의 1차 근거 문서 역할을 한다.
- `ARCHITECTURE.md` Deferred Decision #3(인증/인가 구현 방식)이 확정될 때 참조할 권한 요구사항을 제공한다 — 단, 세션/토큰 등 구현 방식 자체는 이 문서의 범위가 아니다.

---

## 2. 역할 정의

움틀의 사용자는 다음 네 가지 역할 중 하나 이상을 가진다 (`PRD.md` 3장, `DOMAIN_MODEL.md` 3.1과 동일).

| 역할 | 설명 |
|------|------|
| 관리자 (Admin) | 학원 운영 전반을 관리하는 역할 |
| 선생님 (Teacher) | 반과 수업을 담당하고 학생을 지도하는 역할 |
| 학생 (Student) | 학원에 등록되어 학습 활동의 대상이 되는 역할 |
| 학부모 (Parent) | 학생의 보호자로서 학생 관련 정보를 조회하는 역할 |

역할 간 권한 위계(예: 상위 역할이 하위 역할 권한을 포함하는지 여부)는 서술되어 있지 않으며, 4장에 미정 항목으로 남긴다.

---

## 3. 도메인별 권한

각 표는 `REQUIREMENTS.md` 3장의 해당 절을 그대로 표로 옮긴 것이다. 빈 칸은 원본에 서술이 없다는 뜻이며, "권한 없음"으로 단정하지 않는다.

### 3.1 학생 관리 (`REQUIREMENTS.md` 3.1)

| 역할 | 권한 |
|------|------|
| 관리자 | 학생 정보 등록, 조회, 수정, 비활성화 |
| 선생님 | 담당 학생의 기본 정보와 학습 관련 정보 조회 |
| 학생 | 서술 없음 — 4장 참고 |
| 학부모 | 서술 없음 — 4장 참고 |

### 3.2 반 및 수업 관리 (`REQUIREMENTS.md` 3.2)

| 역할 | 권한 |
|------|------|
| 관리자 | 반 생성, 조회, 수정, 비활성화 / 반에 학생·선생님 배정 / 수업 생성, 조회, 수정, 취소 |
| 선생님 | 서술 없음 — 4장 참고 |
| 학생 | 서술 없음 — 4장 참고 |
| 학부모 | 서술 없음 — 4장 참고 |

### 3.3 일정 관리 (`REQUIREMENTS.md` 3.3)

| 역할 | 권한 |
|------|------|
| 관리자 | 학원 운영 일정 등록, 조회, 수정, 삭제 |
| 선생님 | 담당 수업과 관련된 일정 조회 |
| 학생 | 본인과 관련된 일정 조회 |
| 학부모 | 자녀와 관련된 일정 조회 |

### 3.4 출결 관리 (`REQUIREMENTS.md` 3.4)

| 역할 | 권한 |
|------|------|
| 관리자 | 전체 출결 기록 조회 |
| 선생님 | 수업별 학생 출결 상태 기록 및 수정 |
| 학생 | 본인의 출결 기록 조회 |
| 학부모 | 자녀의 출결 기록 조회 |

출결 상태의 종류는 `REQUIREMENTS.md` 3.4에 따라 별도로 정의된다(미정).

### 3.5 숙제 관리 (`REQUIREMENTS.md` 3.5)

| 역할 | 권한 |
|------|------|
| 관리자 | 서술 없음 — 4장 참고 |
| 선생님 | 수업 또는 학생 단위 숙제 등록, 조회, 수정, 삭제 / 숙제 제출·수행 상태 확인 |
| 학생 | 본인에게 부여된 숙제 조회 |
| 학부모 | 자녀의 숙제 현황 조회 |

### 3.6 학습 기록 관리 (`REQUIREMENTS.md` 3.6)

| 역할 | 권한 |
|------|------|
| 관리자 | 학생별 학습 이력 조회 |
| 선생님 | 학생별 학습 기록 작성, 조회, 수정 (담당 선생님은 이력 조회 포함) |
| 학생 | 서술 없음 — 공개 범위 미정, 4장 참고 |
| 학부모 | 서술 없음 — 공개 범위 미정, 4장 참고 |

### 3.7 공지 및 알림 (`REQUIREMENTS.md` 3.7)

| 역할 | 권한 |
|------|------|
| 관리자 | 전체 또는 특정 사용자 그룹 대상 공지 등록 |
| 선생님 | 담당 반 또는 학생과 관련된 공지 등록 |
| 학생 | 본인에게 해당하는 공지 조회 |
| 학부모 | 본인에게 해당하는 공지 조회 |

알림 채널, 발송 조건, 읽음 처리 방식은 `REQUIREMENTS.md` 3.7에 따라 추후 결정된다(미정).

---

## 4. 아직 결정되지 않은 사항

다음 항목은 `REQUIREMENTS.md`와 `DOMAIN_MODEL.md`에도 서술이 없어 이 문서에서 임의로 정의하지 않는다. `REQUIREMENTS.md` 5장, `DOMAIN_MODEL.md` 6장에 따라 구현 전에 확정이 필요하다.

- 학생 관리(3.1)에서 학생 본인·학부모의 접근 권한
- 반 및 수업 관리(3.2)에서 선생님·학생·학부모의 조회 권한
- 숙제 관리(3.5)에서 관리자의 권한
- 학습 기록(3.6)의 학생·학부모 공개 범위
- 공지(3.7)의 채널, 발송 조건, 읽음 처리 방식
- "담당 학생" / "담당 반"의 배정 기준 — 반-학생, 반-선생님 배정 규칙 자체가 `DOMAIN_MODEL.md` 6장에 미정으로 남아 있어, 이 기준이 정해지기 전에는 "담당"의 범위를 시스템적으로 판단할 수 없다
- 학부모와 학생의 연결 방식
- 역할 간 위계(상위 역할의 하위 역할 권한 포함 여부)
- 역할별 권한의 기술적 강제 방식(인가 처리 위치, 세션/토큰 방식 등) — `ARCHITECTURE.md` Deferred Decision #3에서 별도로 다룬다

---

## 5. 변경 원칙

- 이 문서의 권한 내용은 `REQUIREMENTS.md` 3장과 항상 일치해야 한다. `REQUIREMENTS.md`가 변경되면 이 문서도 함께 갱신한다.
- 4장의 미정 항목이 확정되면 해당 항목을 3장의 표로 옮기고 4장에서 제거한다.
- 이 문서에 없는 권한을 구현에서 임의로 가정하지 않는다 — `AGENTS.md`에 따라 확인 후 진행한다.
