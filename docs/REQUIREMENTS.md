# REQUIREMENTS.md

# 움틀 기능 요구사항

이 문서는 움틀(Umtle)의 기능 요구사항을 관리한다. 제품 목표와 범위는 `PRD.md`를 최우선 기준으로 삼는다.

---

## 1. 서비스 목표

움틀은 학원 운영에 필요한 핵심 기능을 하나의 서비스에서 제공하고, 학생의 학습 기록과 성장 과정을 지속적으로 관리할 수 있어야 한다.

---

## 2. 사용자

움틀의 핵심 사용자는 다음과 같다.

- 관리자
- 선생님
- 학생
- 학부모

사용자별 권한과 접근 범위는 `USER_ROLES.md`에서 별도로 정의한다.

---

## 3. 기능 요구사항

### 3.1 학생 관리

- 관리자는 학생 정보를 등록, 조회, 수정, 비활성화할 수 있어야 한다.
- 선생님은 담당 학생의 기본 정보와 학습 관련 정보를 조회할 수 있어야 한다.
- 학생 정보는 반, 수업, 출결, 숙제, 학습 기록과 연결될 수 있어야 한다.

### 3.2 반 및 수업 관리

- 관리자는 반을 생성, 조회, 수정, 비활성화할 수 있어야 한다.
- 관리자는 반에 학생과 선생님을 배정할 수 있어야 한다.
- 관리자는 수업 정보를 생성, 조회, 수정, 취소할 수 있어야 한다.
- 수업은 일정, 출결, 숙제, 학습 기록과 연결될 수 있어야 한다.

### 3.3 일정 관리

- 관리자는 학원 운영 일정을 등록, 조회, 수정, 삭제할 수 있어야 한다.
- 선생님은 담당 수업과 관련된 일정을 조회할 수 있어야 한다.
- 학생과 학부모는 본인 또는 자녀와 관련된 일정을 조회할 수 있어야 한다.

### 3.4 출결 관리

- 선생님은 수업별 학생 출결 상태를 기록하고 수정할 수 있어야 한다.
- 관리자는 전체 출결 기록을 조회할 수 있어야 한다.
- 학생과 학부모는 본인 또는 자녀의 출결 기록을 조회할 수 있어야 한다.
- 출결 상태의 종류는 추후 `DOMAIN_MODEL.md` 또는 별도 정책 문서에서 정의한다.

### 3.5 숙제 관리

- 선생님은 수업 또는 학생 단위로 숙제를 등록, 조회, 수정, 삭제할 수 있어야 한다.
- 학생은 본인에게 부여된 숙제를 조회할 수 있어야 한다.
- 선생님은 숙제 제출 또는 수행 상태를 확인할 수 있어야 한다.
- 학부모는 자녀의 숙제 현황을 조회할 수 있어야 한다.

### 3.6 학습 기록 관리

- 선생님은 학생별 학습 기록을 작성, 조회, 수정할 수 있어야 한다.
- 학습 기록은 학생의 성장 과정을 지속적으로 확인할 수 있는 형태로 누적되어야 한다.
- 관리자와 담당 선생님은 학생별 학습 이력을 조회할 수 있어야 한다.
- 학생과 학부모에게 공개할 학습 기록 범위는 권한 정책에서 정의한다.

### 3.7 공지 및 알림

- 관리자는 전체 또는 특정 사용자 그룹을 대상으로 공지를 등록할 수 있어야 한다.
- 선생님은 담당 반 또는 학생과 관련된 공지를 등록할 수 있어야 한다.
- 사용자는 본인에게 해당하는 공지를 조회할 수 있어야 한다.
- 알림 채널, 발송 조건, 읽음 처리 방식은 추후 결정한다.

---

## 4. 비기능 요구사항

- API 서버는 Kotlin과 Spring Boot를 기반으로 구현한다.
- 데이터 저장소는 MySQL을 기준으로 한다.
- 입력값은 서버에서 검증해야 한다.
- 권한이 없는 사용자는 보호된 데이터에 접근할 수 없어야 한다.
- 핵심 도메인 변경은 테스트로 검증 가능해야 한다.
- 기능은 단순한 구조로 구현하고 불필요한 추상화를 피한다.

---

## 5. 아직 결정되지 않은 사항

다음 항목은 요구사항 확정 전 임의로 구현하지 않는다.

- 사용자별 상세 권한과 역할 범위 — `USER_ROLES.md`에 1차 정리되었으나, 일부 항목은 `USER_ROLES.md` 4장에 미정으로 남아 있다.
- 학생, 반, 수업, 출결, 숙제, 학습 기록의 상세 도메인 모델 — 학생은 `TASK-002`로 최소 필드(이름, 활성 상태)만 확정되었고, 나머지는 여전히 미정이다.
- 출결 상태, 숙제 상태, 수업 상태 등 상태값 정의
- 학부모와 학생의 연결 방식
- 알림 채널과 발송 정책
- 학습 성장 분석 및 시각화의 구체 범위
- API 응답 형식과 에러 코드 규칙

---

## 6. 변경 원칙

- 새 요구사항은 PRD의 목표와 핵심 기능 범위 안에서 추가한다.
- 도메인 정책을 추가하거나 변경할 때는 관련 문서도 함께 갱신한다.
- 요구사항이 불명확하면 구현 전에 확인하고 결정 내용을 문서에 남긴다.
