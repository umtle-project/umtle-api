# ADR-001: 단일 모놀리스로 시작한다

## Status

Accepted (2026-08-05)

- `docs/ARCHITECTURE.md` 2장 "아키텍처 스타일"에 이미 반영된 결정을 ADR 형식으로 공식 기록한다.
- 이 결정을 변경하려면 새로운 ADR을 작성하고 이 문서의 상태를 `Superseded`로 갱신한다.

---

## Context

- `PRD.md`는 움틀을 "학원 운영에 필요한 핵심 기능을 하나의 서비스에서 제공"하는 것을 Primary Goal로 정의하고, Long-term Goal로 학습 데이터 기반 분석/시각화 플랫폼으로의 성장을 제시한다. 두 목표 모두 현재 시점에 조직 규모, 트래픽, 도메인 분리 경계를 예측할 근거를 제공하지 않는다.
- `REQUIREMENTS.md`는 학생/반·수업/일정/출결/숙제/학습 기록/공지 7개 기능 영역을 정의하지만, 5장 "아직 결정되지 않은 사항"에서 상세 도메인 모델, 상태값, 권한 범위 등 다수 항목을 명시적으로 보류하고 있다. 즉 요구사항이 아직 안정화되지 않은 초기 단계다.
- `DOMAIN_MODEL.md`는 8개 도메인(사용자, 학생, 반/수업, 일정, 출결, 숙제, 학습 기록, 공지)을 개념적으로 정의했지만, 각 도메인 간 결합도나 독립 배포 필요성을 판단할 실사용 데이터(트래픽, 팀 조직 구조, 장애 격리 요구 등)가 아직 없다.
- 현재 조직은 단일 백엔드 저장소(`umtle-api`)로 개발되고 있으며, 별도의 팀 분리나 독립 배포 주기에 대한 요구가 문서화되어 있지 않다.
- 이런 상황에서 MSA, 이벤트 기반 아키텍처(Kafka), 별도 캐시 계층(Redis), CQRS와 같은 분산 아키텍처를 먼저 도입하면, 검증되지 않은 도메인 경계를 코드/인프라 수준으로 고정시키는 위험이 있고, `AGENTS.md`의 "단순한 구조를 우선한다", "확장성을 고려하되 불필요한 추상화는 지양한다" 원칙과 충돌한다.
- 따라서 초기 아키텍처 스타일을 어떻게 시작할 것인지 결정이 필요했다.

---

## Decision

- 움틀 백엔드는 **단일 모놀리스(Single Monolith)**로 개발을 시작한다.
- 하나의 Gradle 프로젝트, 하나의 배포 단위로 구성하며, 별도의 서비스 분리나 프로세스 간 통신을 도입하지 않는다.
- 모놀리스 내부는 `ARCHITECTURE.md`에서 정의한 DDD 4-Layered Architecture(Presentation / Application / Domain / Infrastructure)를 따르고, Aggregate 간에는 식별자(ID)로만 참조하며 JPA 연관관계 매핑을 사용하지 않는다.
- 이 내부 구조 원칙(Aggregate 경계, ID 참조, 계층 분리)은 향후 특정 도메인을 별도 서비스로 분리해야 할 필요가 생겼을 때 전환 비용을 낮추기 위한 사전 대비이며, 지금 시점에 분리를 실행하는 것은 아니다.

---

## Alternatives

### 1. 마이크로서비스 아키텍처(MSA)로 시작

- 도메인별(학생, 출결, 숙제 등)로 서비스를 분리하여 독립 배포/확장이 가능하게 한다.
- 기각 사유: 아직 도메인 경계가 실사용을 통해 검증되지 않았고, 조직도 단일 팀 규모다. 분산 시스템의 운영 복잡도(서비스 간 통신, 장애 전파, 데이터 정합성)를 감당할 근거가 없으며, `REQUIREMENTS.md` 5장에 도메인 상세 모델 자체가 미확정 상태라 서비스 경계를 지금 고정하는 것은 위험하다.

### 2. 멀티모듈 모놀리스(Modular Monolith)로 시작

- 단일 배포 단위는 유지하되 Gradle 멀티모듈로 도메인 경계를 물리적으로 분리한다.
- 기각 사유: 현재 도메인 모델과 Aggregate 경계가 아직 확정되지 않아(`ARCHITECTURE.md` 8장 Deferred Decisions 1번) 모듈 경계를 지금 고정하면 잦은 재구조화 비용이 발생한다. 단일 모듈 내에서 계층/패키지 구조로 경계를 지키는 것으로 충분하다고 판단했다. 이 대안은 폐기가 아니라 `ARCHITECTURE.md` Deferred Decisions로 이연되었다.

### 3. CQRS 도입

- 명령(Command)과 조회(Query) 모델을 분리하여 학습 기록/분석과 같은 조회 중심 기능을 최적화한다.
- 기각 사유: 현재 조회 성능이나 모델 복잡도 문제가 실측되지 않았고, PRD의 Long-term Goal(학습 데이터 분석)도 아직 구체적 범위가 없다(`REQUIREMENTS.md` 5장). 근거 없는 조기 최적화로 판단하여 제외했다.

### 4. Redis 캐시 계층 도입

- 조회 성능 향상을 위해 캐시 계층을 선도입한다.
- 기각 사유: 현재 트래픽/조회 부하에 대한 데이터가 없고, MySQL 단일 저장소로 요구사항을 충족할 수 있다고 판단했다.

### 5. Kafka 기반 이벤트 아키텍처 도입

- 도메인 간 정합성(예: 학생 비활성화 시 관련 도메인 처리)을 이벤트로 비동기 처리한다.
- 기각 사유: 여러 Aggregate 동시 변경 처리 전략 자체가 아직 미정(`ARCHITECTURE.md` 8장 Deferred Decisions 2번)이며, 메시징 인프라를 운영할 근거도 없다.

---

## Consequences

### 긍정적 결과

- 초기 개발 속도가 빠르다 — 단일 배포, 단일 트랜잭션 범위로 구현/테스트/배포가 단순하다.
- 분산 시스템에서 발생하는 네트워크 장애, 데이터 정합성, 관측성(observability) 문제를 초기에 다루지 않아도 된다.
- `AGENTS.md`의 "단순한 구조를 우선한다", "확장성을 고려하되 불필요한 추상화는 지양한다" 원칙과 부합한다.
- Aggregate 간 ID 참조, JPA 연관관계 미사용 원칙을 지금부터 지키면, 실제로 분리가 필요해질 때(트래픽 증가, 팀 분리 등) 전환 비용을 낮출 수 있다.

### 부정적 결과 / 트레이드오프

- 특정 도메인(예: 학습 기록 분석)의 부하가 커져도 해당 부분만 독립적으로 확장할 수 없다 — 전체 애플리케이션 단위로 스케일링해야 한다.
- 하나의 배포 단위이므로 한 도메인의 배포가 전체 서비스 배포에 영향을 줄 수 있다.
- Aggregate 경계와 ID 참조 원칙을 지키지 않으면(예: 편의를 위해 JPA 연관관계를 슬쩍 추가하는 등) 이후 서비스 분리가 사실상 불가능해질 수 있다 — 코드 리뷰에서 지속적으로 검증이 필요하다.
- MSA/Kafka/Redis/CQRS로의 전환 시점과 기준이 아직 정의되어 있지 않다 (`ARCHITECTURE.md` 8장 Deferred Decisions 7번과 연결).

### 후속 조치

- 모듈 분리 및 MSA 전환을 판단할 기준(트래픽, 팀 구조, 장애 격리 요구 등)이 정해지면 별도 ADR로 재논의한다.
- 이 결정은 `docs/DECISIONS.md`에도 한 줄로 요약되어 있다.
